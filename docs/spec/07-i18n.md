# SPEC-07 — Quốc tế hoá (vi / en)

Liên quan: `prd/05-i18n-and-nfr.md §1`

## 1. Ba tầng nội dung

| Tầng | Nơi lưu | Cách dịch | Ai chịu trách nhiệm |
|---|---|---|---|
| UI chrome (nhãn, nút, lỗi, email) | `packages/i18n/locales/{vi,en}/*.json` | Thủ công, review bởi người | Dev + người review ngôn ngữ |
| Nội dung hệ thống (Place, danh mục, chính sách) | MongoDB, trường `{ vi, en }` | Admin nhập cả hai | Admin |
| Nội dung người dùng (post, comment, tin nhắn) | MongoDB, một trường + `lang` | Không dịch sẵn; dịch theo yêu cầu bằng Gemini, có cache | Hệ thống |

## 2. UI chrome

### 2.1 Thư viện

- `web`: `next-intl` (hỗ trợ App Router, server component, ICU MessageFormat sẵn).
- `api` / `worker`: `i18next` với cùng bộ file JSON để dựng email, push, và `error.message`.

Dùng chung một nguồn file dịch ở `packages/i18n` để không lệch nội dung giữa web và email.

### 2.2 Tổ chức file

```
packages/i18n/
├── locales/
│   ├── vi/  common.json  auth.json  feed.json  post.json  planner.json
│   │        messaging.json  agency.json  business.json  guide.json
│   │        admin.json  errors.json  emails.json  validation.json
│   └── en/  (cùng danh sách file, cùng danh sách key)
├── src/
│   ├── index.ts          # export getTranslator, formatters
│   ├── formats.ts        # định dạng ngày, số, tiền theo locale
│   └── types.ts          # type sinh từ file vi (nguồn chuẩn về key)
└── scripts/
    ├── check-missing.ts  # so key giữa vi và en
    ├── check-unused.ts   # tìm key không được dùng trong code
    └── extract.ts        # tìm chuỗi hard-code trong JSX/TS
```

### 2.3 Quy ước key

```
<domain>.<screen|component>.<element>[.<state>]

post.composer.placeholder
post.composer.submit
post.composer.error.tooLong
planner.quota.exhausted.title
errors.VALIDATION_ERROR
emails.verifyEmail.subject
validation.password.tooShort
```

Không dùng câu tiếng Anh làm key (`"Sign in"`) — khi sửa văn bản gốc phải sửa key ở mọi nơi, và key mất ý nghĩa khi văn bản dài.

### 2.4 ICU MessageFormat

Tiếng Việt không biến đổi số nhiều, tiếng Anh có. Dùng ICU để cùng một key xử lý cả hai:

```json
// vi/feed.json
{ "reactions": "{count, plural, other {# lượt thích}}",
  "commentedOn": "{name} đã bình luận bài viết của {author, select, self {bạn} other {{author}}}",
  "timeAgo": "{minutes, plural, other {# phút trước}}" }

// en/feed.json
{ "reactions": "{count, plural, =0 {No likes} one {# like} other {# likes}}",
  "commentedOn": "{name} commented on {author, select, self {your} other {{author}'s}} post",
  "timeAgo": "{minutes, plural, one {# minute ago} other {# minutes ago}}" }
```

Tiếng Việt bắt buộc phải có nhánh `other`; nếu chỉ khai báo `one` thì ICU sẽ lỗi vì tiếng Việt luôn map về `other`.

### 2.5 Kiểm tra tự động (CI chặn merge)

| Kiểm tra | Công cụ | Ngưỡng |
|---|---|---|
| Key có ở `vi` nhưng thiếu ở `en` (và ngược lại) | `check-missing.ts` | 0 key thiếu |
| Chuỗi hard-code trong JSX | ESLint `i18next/no-literal-string` | 0 vi phạm |
| Key được dùng trong code nhưng không tồn tại trong file | Type generation từ `vi` | Lỗi TypeScript |
| Key không được dùng ở đâu | `check-unused.ts` | Chỉ cảnh báo |
| Placeholder lệch nhau giữa hai locale | `check-missing.ts` | 0 lệch (ví dụ `vi` có `{name}` mà `en` không) |

Type-safe key: script sinh `type TranslationKey = 'post.composer.submit' | ...` từ file `vi`. Gõ sai key là lỗi compile, không phải lỗi runtime.

## 3. Xác định locale

Thứ tự ưu tiên: `user.locale` (đã đăng nhập) → cookie `NEXT_LOCALE` → `Accept-Language` (thương lượng với danh sách hỗ trợ) → `vi`.

Middleware Next.js đọc theo thứ tự trên và đặt cookie. API đọc `Accept-Language` do client gửi; với email và push, **luôn** dùng `user.locale` của người nhận, không dùng locale của request đang xử lý — đây là lỗi dễ mắc khi người A (en) gây ra thông báo cho người B (vi).

Đổi locale: `PATCH /me { locale }` → cập nhật DB + cookie → client `router.refresh()`. Không cần đăng nhập lại.

## 4. Định tuyến & SEO

Chiến lược: **prefix cho `en`, không prefix cho `vi`** (`localePrefix: 'as-needed'`). Người Việt là phần lớn lưu lượng nên URL sạch hơn cho họ.

```
vi:  /                /dia-diem/da-nang       /kham-pha    /ke-hoach
en:  /en              /en/places/da-nang      /en/explore  /en/planner
```

Slug bản địa hoá: `Place` lưu `slug` chung (`da-nang`) và pathname được dịch qua bảng `pathnames` của next-intl. Slug ID-based cho tài nguyên do người dùng tạo (`/posts/:id`) để đổi tiêu đề không phá link.

Thẻ SEO bắt buộc trên mọi trang công khai:

```html
<link rel="canonical" href="https://travelvietplaner.com/dia-diem/da-nang" />
<link rel="alternate" hreflang="vi" href="https://travelvietplaner.com/dia-diem/da-nang" />
<link rel="alternate" hreflang="en" href="https://travelvietplaner.com/en/places/da-nang" />
<link rel="alternate" hreflang="x-default" href="https://travelvietplaner.com/dia-diem/da-nang" />
```

Sitemap tách theo locale (`/sitemap-vi.xml`, `/sitemap-en.xml`), khai báo trong `/sitemap.xml` index. OG tags theo locale (`og:locale`, `og:locale:alternate`).

## 5. Định dạng

| Loại | vi | en | Ghi chú |
|---|---|---|---|
| Ngày | `03/08/2026` | `Aug 3, 2026` | |
| Ngày + giờ | `03/08/2026 14:30` | `Aug 3, 2026, 2:30 PM` | |
| Tương đối | `2 giờ trước` | `2 hours ago` | Chuyển sang ngày tuyệt đối sau 7 ngày |
| Tiền VND | `1.500.000 ₫` | `₫1,500,000` | Dùng `Intl.NumberFormat` |
| Số | `1.234,56` | `1,234.56` | |
| Khoảng ngày | `3 – 6/8/2026` | `Aug 3 – 6, 2026` | `Intl.DateTimeFormat.formatRange` |
| Tên người | `displayName` nguyên bản | như vi | Không đảo thứ tự họ tên |

**Hướng viết (directionality)**: cả `vi` và `en` đều LTR. Nền tảng **không hỗ trợ RTL** ở v1 (không có ngôn ngữ Ả Rập/Do Thái); `dir="ltr"` cố định, không dùng logical CSS properties bắt buộc. Ghi nhận rõ để loại khỏi phạm vi test và không phát sinh chi phí layout mirroring; nếu thêm ngôn ngữ RTL sau này, đây là điểm cần mở lại.

Múi giờ: **lưu UTC, hiển thị theo `user.timezone`** (mặc định `Asia/Ho_Chi_Minh`). Ngày trong itinerary là ngày địa phương của điểm đến, lưu dạng `YYYY-MM-DD` không kèm giờ để tránh lệch ngày khi đổi múi giờ. Quota planner reset 00:00 giờ VN cho mọi người dùng để logic tính hạn mức đơn giản và kiểm chứng được.

## 6. Nội dung hệ thống trong DB

Trường đa ngôn ngữ: `{ vi: String, en: String }`. Quy tắc đọc: `value[locale] || value.vi || value.en || ''` — luôn có nội dung hiển thị, ưu tiên tiếng Việt làm nguồn chuẩn.

Validation ở admin: `vi` bắt buộc, `en` bắt buộc với Place `published` và mọi văn bản chính sách; cảnh báo (không chặn) với các trường mô tả phụ. Admin UI hiện hai tab vi/en cạnh nhau, đánh dấu trường còn thiếu.

Mẫu email/push lưu trong `packages/i18n/locales/*/emails.json`, có preview song ngữ trong admin console.

## 7. Nội dung người dùng

### 7.1 Nhận diện ngôn ngữ

Khi đăng bài: nhận diện bằng heuristic dựa trên ký tự đặc trưng tiếng Việt (dấu thanh, `đ`, `ơ`, `ư`) + tần suất từ khoá phổ biến. Đủ chính xác cho hai ngôn ngữ và không cần gọi API. Kết quả lưu vào `post.detectedLang`; người đăng sửa được `post.lang`.

Dùng để: hiển thị nút "Dịch bài này" chỉ khi `post.lang !== user.locale`, và làm tín hiệu nhẹ cho xếp hạng feed (không lọc cứng — người dùng song ngữ vẫn muốn thấy cả hai).

### 7.2 Dịch theo yêu cầu

```
POST /v1/translate { targetKind: 'post'|'comment', targetId, targetLang }
→ { translated, sourceLang, cached: true|false, provider: 'gemini' }
```

Cache ở MongoDB `translations { targetKind, targetId, targetLang, contentHash, text, createdAt }`, unique index `(targetKind, targetId, targetLang, contentHash)`. `contentHash` để bản dịch tự vô hiệu khi tác giả sửa bài. Rate limit 30 lần/giờ/user.

Không dịch tin nhắn riêng tư tự động (gửi nội dung riêng tư tới bên thứ ba cần sự đồng ý rõ ràng) — có nút dịch thủ công kèm cảnh báo lần đầu.

UI hiển thị bản dịch: thay thế nội dung gốc, kèm nhãn "Đã dịch bằng AI" và nút "Xem bản gốc".

## 8. Tìm kiếm không dấu

Yêu cầu: "da nang", "Đà Nẵng", "ĐÀ NẴNG", "đà nẵng" cho cùng kết quả.

Elasticsearch xử lý bằng `icu_folding` + mapping `đ→d` (chi tiết `spec/04-search.md §1`). MongoDB (fallback và autocomplete cục bộ) lưu thêm trường `searchNormalized`: bỏ dấu bằng NFD + xoá dải combining marks + `đ→d` + lowercase, index thường trên trường này.

Chuẩn hoá Unicode: **NFC** cho mọi text lưu vào DB. Tiếng Việt có hai cách biểu diễn ("ế" = 1 code point hoặc "e" + dấu mũ + dấu sắc); không chuẩn hoá thì hai chuỗi trông giống nhau lại không khớp khi so sánh hay tìm kiếm. Áp dụng ở middleware validate của `api`, không để từng chỗ tự làm.

## 9. Planner song ngữ

- Ngôn ngữ trả lời = ngôn ngữ câu hỏi (nhận diện mỗi lượt), không phải `user.locale` — người dùng có thể hỏi tiếng Anh trong tài khoản tiếng Việt.
- Retrieval **không lọc cứng theo ngôn ngữ**: filter `lang IN [detectedLang, 'en']`. Tài liệu tiếng Việt vẫn hữu ích cho câu hỏi tiếng Anh; LLM dịch khi tổng hợp.
- Citation ghi rõ ngôn ngữ gốc của tài liệu: "Cẩm nang Đà Nẵng (tiếng Việt)".
- Nhãn trạng thái stream (`status` event) gửi cả hai bản `{ vi, en }`, client chọn hiển thị.
- Bộ test chất lượng có 100 câu mỗi ngôn ngữ, gồm các ca chéo ngôn ngữ (hỏi en, nguồn vi).

## 10. Acceptance Criteria

- AC-01: `pnpm i18n:check` phát hiện đúng key thiếu, placeholder lệch, và fail CI.
- AC-02: ESLint chặn commit có chuỗi tiếng Việt/Anh hard-code trong JSX.
- AC-03: Người dùng `en` nhận email tiếng Anh khi người dùng `vi` bình luận bài của họ.
- AC-04: `/dia-diem/da-nang` và `/en/places/da-nang` cùng render, có `hreflang` và canonical đúng.
- AC-05: Tìm "da nang" và "Đà Nẵng" trả cùng tập kết quả với thứ tự tương đương.
- AC-06: Bài viết chứa "ế" ở dạng NFD được lưu về NFC và tìm thấy khi gõ dạng NFC.
- AC-07: Hỏi planner bằng tiếng Anh trong tài khoản locale `vi` → trả lời tiếng Anh, citation ghi rõ nguồn tiếng Việt.
- AC-08: Sửa nội dung bài → bản dịch cache bị vô hiệu, lần dịch sau trả nội dung mới.
- AC-09: Đổi locale trong Cài đặt → UI, email kế tiếp, và câu trả lời planner đổi theo, không cần đăng nhập lại.
- AC-10: Giá `1500000` hiển thị `1.500.000 ₫` ở `vi` và `₫1,500,000` ở `en`.
- AC-11: Không có chuỗi bị cắt/tràn (overflow) trên các màn hình chính ở cả hai locale. Test visual regression chạy pseudo-locale "dài" (mô phỏng chuỗi dài hơn ~35%, ví dụ tiếng Đức) để bắt sớm nút/nhãn tràn — dù v1 chỉ có vi/en, EN thường dài hơn VI trên nút hành động. Component phải chịu được text dài (không `white-space: nowrap` cứng, cho phép wrap/truncate có kiểm soát).
